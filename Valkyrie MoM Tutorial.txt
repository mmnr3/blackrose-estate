Installing Prerequisites
First off install Steam and download the Mansions of Madness App, from here:
http://store.steampowered.com/app/478980/Mansions_of_Madness/
Go to the GitHub for Valkyrie and install it:
https://github.com/NPBruce/valkyrie/wiki


Fire up Valkyrie and under Mansions of Madness Second Edition hit Import Content
  

You should see this after the import is complete.


It can take some time as it collects all of the data from the Steam App, so be patient.


Once done click Mansions of Madness Second Edition.




Select Content
In this section you can select all of the game components you own. It is assumed that you own the main game (MoM Second Edition).


If you own an expansion, figure packs or even Mansions of Madness First Edition, you can select them here. Don’t forget to do this as it will open up more options for Scenarios when you come to download them (now and in the future as people add them).
Downloading Premade Scenarios
If you’re not interested in making a Scenario just yet you can play some of the awesome Scenarios that the community has already made and published.


To do this click on Start Scenario then click Download
  

Select the Scenario that you want to download, any that are already downloaded will be greyed out.
Tip - You can use this section to Delete any Scenarios that you have downloaded from your machine.
Click Back once you have downloaded all the Scenarios that you want and you should have a list available.
Click the one you want to play:
  

Playing the Scenario works exactly like the Official App from this point on.

Editor Navigation
Before I get into the guts of the Editor, I wanted to quickly explain how to navigate it. The actual use of the Editor is straightforward, but there are some navigation options that make life a lot easier.
  

1) The Scenario and Components button serve the same function, they open the Components menu, this menu is the most used section:
  

2) Save & Test can be used to sample your Scenario at any time. This allows you to run it as a player would see without having to save and exit. More about this later.
3) “Tools” is self explanatory, Reorder Components is handy for organizing your tiles/tokens/etc. But generally speaking you won’t use this much.
4) Menu - Can be used to save, etc, etc.


While using the Editor; creating events, tokens, spawns (etc), there are some useful buttons that you can use to navigate.
  
  

1) Back Button, this will take you to the previous item you were on.


2) Go to Component, clicking this will take you to the Component if refers to (event, item, puzzle spawn, etc).


3&4) Clicking the + icon for an event will give you the option to create a {new} one.


These buttons significantly streamline navigation of your Scenario, so I would encourage you to learn how they function.
Creating Tiles and Tokens

To add either of these to the game, you must select them from the Add Components option in the event (spawn, etc) you wish them to appear in.

Use Rotation if you want it placed in a different orientation.

Scenario phases
Contributed by Anton Timmermans


After adding tiles and tokens in the editor it is time to add a flow to the scenario that makes the scenario come alive. For this flow it is important to remember the phases of the game:
  

Some automatic triggers mark the beginning or end of a phase. These triggers can be used to activate events in your scenario.


How that works is explained in the next chapter with an example how to place the first tile.


Note that for Decent only StartRound and EndRound are used.








Important for Mansion of Madness: 
* An event triggered by the Mythos trigger does not replace the default Mythos events which are set by a variable (see chapter Mythos Events). If both the default Mythos and a user generated event with the Mythos trigger are active, the order in which they occur is also not fixed. So default Mythos can be handled before or after this trigger is set. Therefor, for predictive behaviour of your scenario, it may be better to use the BeforeMonsterActivation trigger which is ALWAYS after the mythos phase.
* The trigger EndInvestigatorTurn is most useful in an event to check if any conditions are met to change Mythos events which are set by a variable (see chapter Mythos Events), or to determine if end of scenario contidtions are met.
* The trigger Eliminated is activated when a full investigator turn is completed. So, if in round 15 the menu option ‘Investigator Eliminated’ is selected, a full round 16 is handled, and THEN this trigger is set. Note that if there is an event linked to this trigger, it will be called once. If the scenario is not ended after handling this event,the investigators will need to hit the End turn button again after which the EndInvestigatorTurn is called again and the game continues as normal. The menu option ’Investigattor Eliminated’ will remain grayed out.

Like Tiles and tokens, you have to first create the item before you can add it as a component.
Common Items, Spells and Unique items are created and given to players in the same way.


I’ve split this into 4 categories, to try to explain the different ways of distributing items.

Using built-in sound effects and music
.(contributed by anton timmermans)


Using built-in sound effects and music is not very complicated. You simply click either the box Audio or the + behind Music and you can select from the list of sounds that Valkyrie provides. Using the correct sound effects on token selection, or triggered events adds much to the suspense in your scenario, so use it frequently but also use it well.
  

Audio
The field audio is typically used for short sound effects like shutting doors, opening gates, breaking glass. If here is background music playing or any other sounds, that sound is left undisturbed and the new sound effect is added.  Even if you have two fast events triggered in succession, and each of those events has their own sound effect, then the second sound is added to whatever sound may still be playing. Every sound selected in the audio field will continue playing until it is completed.
Music
The music field is typically used for background music. The main difference between the music selection and the audio field is that the selected sound in the music field is stopped (faded out) and replaced with any new sound selected in the music field of a next event.
Example usage: This field should typically be used when you add your own narrative to the introduction text (see also Custom Audio). This allows players to stop the narrative playback if they choose not to wait for it to end and want to skip placing the starting tile. To stop the music playback, add in the next event the sound you want to replace current playback with. This can be any sound, including a custom made sound with for example 1 sec. silence.

Quest Variables
These are custom variables that are set by players with the Assign option in the editor Elements (events, UI, Spawns, etc). 


Quest Variables cannot contain special characters or spaces.
How are they used
Variables are used in the Tests and Assign sections of most elements (Events, Tokens, Spawns, etc).


Tests
A test can be used as criteria for an Event or Spawn (or any of the other Elements that have Tests as an option), if the criteria is met the Event or Spawn will run, if not it will be ignored.


Contributed by antontimmermans For example if you want to increase variation on your scenario and want to use alternative monsters or conditions from an expansion, you need to check if the expansion is available. For example: You can test in the event #HJ == 1 if you want to spawn Dimensional Shambler instead of a Ghost.
Note that if a figure and tile collection is set, also the first edition set with the corresponding symbol is set (example: #SM →  #CotWI, #CotWT, #CotWM, #FAI, #FAT, #FAM). Therefore advised to test for the 1st edition set presence in case someone has only one of those sets (example:#CotWI, #CotWT, #CotWM).


Assign
Assign is used in Events or Spawns (or any other element that has the Assign option), to set a variable. For example you can assign 1 to the $fire variable to toggle on the “Fire Spreads” Mythos Event.

How Mythos Events work in the App
Mythos is flavour text and events that happens in the Mythos Phase, which is after the Investigator Phase and before the Monster Phase. They are binary variables that you turn On (1) or Off (0), the default state of these variables is Off (0). 


If at least one Mythos Event is turned on, they will begin to appear in the Mythos phase and every subsequent mythos phase until they are all turned off.


Note: Think of this like a “flag”, if you turn on a $mythos variable you are instructing Valkyrie to run mythos events automatically. If you turn off all $mythos variables, you are instructing Valkyrie to no longer run them for you.


In Valkyrie these variables are symbolised as “$” Vars, they can only be turned on or off.
(we touched on this above)


Mythos Event variables are as follows (best to worst):


$mythoshelp - Gives helpful events for Investigators (heals, become focus, etc)
$mythosflavour - Gives flavour text, that generally doesn’t effect the investigators.
$mythosminor - Gives Minor mythos events, generally easy tests as bad stuff happens.
$mythosmajor - Gives Major mythos events, generally moderate tests as bad stuff happens.
$mythosdeadly - Gives Deadly mythos events, generally hard tests as very bad stuff happens. 


In pretty much all elements (Events, Spawns, Tokens, UI, etc) you can Assign a number (or another variable!). For Mythos Events that would be to Assign a “1” (on) to one or more of the $MythosLevel variables.

Some actions in the game may require a check of a skill (strength, agility, ...) to determine the result. For example: to break open a door (test strength) or to catch a piece of paper fluttering around in a dust-devil (agility or observation). Creating Custom Puzzles using UI
It's possible to create your own custom puzzles by placing and removing UI elements. Just think of any interactive puzzle as a series of removing and replacing images. You can use Event Loops to achieve this.


This section is quite complex and even writing this I am struggling to simplify it into an overview.. So here goes.


You want your events to do the following things:


* Place a pretty background
* Set some variables, the position of objects and the ultimate goal of the puzzle (aka a lock combination or an order of objects).
* Place some movable objects (Using an event loop to give multiple positions)
* Place some buttons (using transparent UI elements, with a temporary border so you can see where they are). Laying these over the already placed objects means you can always click them.
* Create event loop ends to clean up temporary tracking variables.


The idea here is to place some objects and lay over some buttons. The buttons can be clicked to remove UI elements and/or update variables to make the puzzle interactive.


Each time a button is clicked you want to change some tracking variables and rerun the loop. For example you may click Object_1’s button (lets assume it's in position 1), which removes all UI elements of Object_1 and then adds +1 to the variable Object_1_Position. When the event loop is rerun, Object_1 is now in position 2, since it's position variable is now 1 higher.

Create your puzzle images
With any good puzzle you will first need some good images, I would recommend that before you even get to Valkyrie coding that you build your puzzle in GIMP. This is a free “photoshop” alternative that can be used to create your PNG images and each part of your puzzle.


I won’t go into the full details of how to use GIMP, but the core feature you need to understand is Layers.
You can use the right hand bar to make layers and then use the little “eye” to hid them. This is a very useful function, but for puzzles it allows you to create each “object” and then duplicate it to move it slightly. 
  

  

You can then Export whatever is visible on your screen, using the File > Export option, here you can select a PNG.


Don’t forget when creating your project to select a transparent background, if you forget you can add transparency to any layer by right clicking the layer and clicking Add Alpha Channel.
  



Use the layers to create your background and any objects (in their own layers), hide layers to work on each object's position (duplicating what you need).


You should be able to simulate your puzzle and how it works using the hide layer function, since what we will be doing in Valkyrie is just coding how to control which of these layers are visible.

Creating a Combination Lock Puzzle
In the previous step I used GIMP to create a background image for my puzzle, I have chosen this puzzle because it doesn’t require many UI elements. Once you understand the concepts of creating puzzles you’ll be able to create more graphically rich puzzles.


Note: I’ve made the first part a little more complicated than it needs to be to better explain how event loops work in a puzzle context, if you are removing and replacing UI elements with rich images you want to do so as efficiently as possible, so having the granularity to remove just one image and place a new one, will save on processing power and help avoid crashes.


Open Valkyrie and create a trigger event for your puzzle. I tend to prefix all of my puzzle events with a prefix, in this example i’ll use CP (combination puzzle). 


I’ll call my event CP_START.
In this event create two UI Elements in this order:


CP_BG_Black, in this UI element you want to make a black background that you can lay the image over. In the UI element, set the Size to 2, Units to Vertical and then the UI’s background to Black.
  





CP_BG_Image, then set it as the combination lock image.
  



Note: When laying UI elements I would always use “Vertical” unit scaling, this will stretch the image (at size 1) to the top and bottom, this will ensure that your images don’t clip off the top when using widescreen resolutions.


In the Continue button, then create two events:


* CP_SetVars - One off event, used to set the combination for the lock and initialise all the variables required.
* 0_CP_Code_CHAINSTART - The first event loop to place the combination locks displayed numbers. 


Note: I have prefixed a “0_” in this event so that when sorting events I can bring this to the top. I use this technique a lot in event loops, as after every event in a loop, you need to reference back to the first event in the loop. Once complete you can always remove the prefix without breaking anything.


Open CP_SetVars in here Assign the following variables.


CP_Answer_n1 = 9
CP_Answer_n2 = 8
CP_Answer_n3 = 7
CP_Answer_n4 = 6
These are the numbers required in the combination lock to open it.
CP_Code_n1 = 1
CP_Code_n2 = 1
CP_Code_n3 = 1
CP_Code_n4 = 1
These are the numbers that will display on the lock.


CP_SetVars = 1
This variable signifies that you have Set the Variables and not to run this again.

Tile Placement and Planning 
This section was kindly written and submitted by Anton. (thanks Anton!) 
It gives some tips on how to pre-plan and organise tile placement chains.
Start-up behavior of a scenario
How to start creaton of a new scenario is nicely explained in the chapter Creating a Scenario - The Basics. While creating the initial events you should consider that from the official FFG application we are (getting) used to start up in a default behaviour. In Valkyrie you have a lot of freedom in the scenarios behaviour, but if you wish to mimic the standard application flow then this sequence of events is suggested:


1. QStartEvent  - triggered by EventStart
   1. Can be a ‘silent event’ and used to initialize your variables.
   2. Calls the event(s) to hand out Clue(s).
2. QHandOutCluex - called by QStartEvent
   1. To mimic the standard Mansions of Madness application’s behavior you should hand-out your Clue tokens 
   2. If you wish to tune your scenario difficulty a little you can do it in this step by handing out a more clue tokens for 3 or less players. Example: Each of the following events is called by QStartEvent and puts up a dialogue instructing to hand out 1,2 or 3 clue(s). Each of the events has a Continue button and will call the QIntroduction.
      1. QHandOutClues1 (test #heroes >= 4)
      2. QHandOutClues2 (test #heroes == 3)
      3. QHandOutClues3 (test #heroes <= 2)
3. QIntroduction - called by QHandOutCluex 
   1. Build-up your Introduction UI and story as explained in UI Elements
Systematic and robust tile placement.
To make the in-game-tile-placement-flow-experience a bit easier and faster for player to handle, the order placement of a room tile and items on it should always be the same. The players will get into the ‘rhythm’ of which type of tokens to place next. Therefore I would suggest to always have a basic placement scheme in place.
This standard placement scheme may look a bit elaborate, but for me it has proved useful. Especially when you have a lot of conditional placements like: “place the Secret Door Token only if the secret door is found”, “place a Search Token if a secret door is not found yet”, “Place an explore token only if the tile to which it connects is not revealed yet”, “place a person token only in round 3”
The standard placement scheme also makes it easier to find the event in your event list while you are programming/debugging your scenario (assuming you alphabetically sort the list).
 
I found the following sequence to be most practical. For example:
 
EventOfficePlaceTile                         (Place the Office tile including dialogue)
->EventOfficePlaceDecoration           (Place walls and doors - no dialogue)
->EventOfficePlaceConnections         (Place Explore and/or Sight Tokens - no dialogue)
->EventOfficePlaceItems                  (Place Search and/or Interaction tokens - no dialogue)
->EventOfficePlacePeople                (Place person tokens or spawns - no dialogue)
->EventQMoveOneSpace                 (Special event handling the "move one space dialogue" that will be explained in a separate chapter)
 
Each placement event would always call the next placement event phase to make the flow robust. This means that the second event in will call the third etc.:
 
EventOfficePlaceTile                         (Place the Office tile including dialogue)
->EventOfficePlaceDecoration  
 
EventOfficePlaceDecoration
->EventOfficePlaceConnections
 
EventOfficePlaceConnections
->EventOfficePlaceItems
Etc…
 
Now this sequence only places the Office tile with some dialogue, but all other placement events do not place anything YET. Let us say I want to place a Wall Token and a Secret Door Token (only if the secret door is discovered).
Then the sequence would look like:
 
EventOfficePlaceDecoration          (no dialogue)
->EventOfficePlaceWall                     (Place Wall Token including dialogue)
->EventOfficePlaceSecretDoor           (Place Secret Door Token including dialogue)
->EventOfficePlaceConnections         (always call the next placement phase)
 
EventOfficePlaceWall                       (Place Wall Token including dialogue)
->EventOfficePlaceSecretDoor        
->EventOfficePlaceConnections         (always call the next placement phase)
 
EventOfficePlaceSecretDoor           (Place Secret Door Token including dialogue; add the test if the secretdoor is found.)
->EventOfficePlaceConnections         (always call the next placement phase)
 
The sequence above would only execute the event EventOfficePlaceSecretDoor if the test on the variable were successful. If TRUE, then the placement and dialogue take place and the next event will be called (EventOfficePlaceConnections). If the test is FALSE, then this event will not be executed but the calling event EventOfficePlaceWall will then call EventOfficePlaceConnections.
 
This might look as if EventOfficePlaceDecoration is an empty and useless event, but it is a placeholder for placement of these type of items. If you later decide to add more decoration (an extra door for example), or want to find a particular event for debugging your scenario, you will know where to look without much thinking.
Calling the next standard placement event phase (in this case EventOfficePlaceConnections) at the end  of each placement even will guarantee proper handling of placement and has low chance of programming mistakes.

EventQMoveOneSpace
When writing the scenario “disturbance at the Docks” that gave a lot of freedom to players to move around however they would like, I stumbled upon the problem that a tile could be entered via different entrances. The problem is then, to make a simple (single) tile placement event sequence with a consistent behavior, that allows the players to “move one additional space”
My specific example uses the Yard4 tile that can be reached via the market tile or from the root cellar. When entering from the market you would use a Sight Token, which should not allow you to move one additional space. When entering from the root cellar you would use an explore token, which should allow the player to move one additional space.
That is how I came up with the EventQMoveOneSpace  (I typically use ‘Q’ to identify all generic Quest events that are not connected to tiles, tokens or rounds). This event is ALWAYS called at the end of placing ANY tile.  (see also my description of Systematic and robust tile placement)
The EventQMoveOneSpace does the following:
1.       Displays the dialogue “You may move one additional space in the revealed area”.
2.       Has a test: MoveOneSpaceAllowed != 0
3.       Assign: MoveOneSpaceAllowed = 0
4.       Continue
 
This means that the text is only displayed if the variable is set to 1 (or any other value then 0). And then flips the variable back 0 so that you don’t accidentally display the text then next time it is called. Make sure initialize this MoveOneSpaceAllowed to 0 in your start event (which I would call EventQStart).
 
Now the trick is to set the variable before the EventPlaceYard4Tile is called. This happens when you select to tokens connecting to this tile:
 
TokenSightMarketYard4:
1.       Dialogue: “The busy market next to the quiet small city park are quite in contrast. An Investigator adjacent to this token may reveal the next area”
2.       Button “Continue”: EventPlaceYard4Tile
3.       Button “Cancel”: <nothing>
4.       Assign: MoveOneSpaceAllowed = 0
TokenExploreRootcellarYard4:
1.       Dialogue: “Moss is covering this rotten door”.
2.       Button {action} Open: EventPlaceYard4Tile
3.       Button “Cancel”: <nothing>
4.       Assign: MoveOneSpaceAllowed = 1

Multiple entry possibilities to a tile
When allowing Investigators to move around freely you will bump into the puzzle of how to deal with tile placement when investigators explore from tile A to tile B, but also have the option to go the other way around. The trick to solve this is to add a test to tile placement. The connecting explore (or sight) token would then have to call both tile placement events but the tile placement events would have to test if they are not already revealed.
Example:
Players may have discovered the RootCellar tile and want to open a door to the Yard4 tile, or the other way around. The connecting explore token would then look something like this:
 
TokenExploreRootCellarYard4:
1.       Dialogue: “Moss is covering this rotten door”.
2.       Button {action} Open: EventYard4PlaceTile, EventRootCellarPlaceTile
3.       Button “Cancel”: <nothing>
4.       Assign: MoveOneSpaceAllowed = 1  (<- see chapter on EventQMoveOneSpace)
 
The tile placement events will then have to include a test if it is not already revealed:
EventRootcellarPlaceTile
1.       Tile placement actions (see also Systematic and robust tile placement)
2.       Test: RootcellarRevealed == 0
3.       Assign: RootcellarRevealed = 1
EventYard4PlaceTile
1.       Tile placement actions (see also Systematic and robust tile placement)
2.       Test: Yard4Revealed == 0
3.       Assign: YardRevealed = 1
 
A consequence of investigators moving around freely, is that when you place a tile you need to test if a connection token (explore- or sight token) must be placed or not. Use the <tile>Revealed variable to test the conditional placement of these connection tokens.
Make sure to initialize all <Tile>Revealed variables to 0 in your start event.

Organizing your events
Contributed by antontimmermans


All your events will be stored in %appdata%Valkyrie\MoM\Editor\<ScenarioName>\event.ini. As your scenario grows you might want to group events related to each other: There are two ways of doing that:
1. Use a systematic naming convention.
2. Group the events into separate *.ini files


I found the best way to deal with events in large scenarios is to apply both methods.


Systematic naming convention
A systematic naming convention of your events give the advantage that you can find your event faster in the list of events when you sort the list alphabetically. 
  

A nice example of naming convention can be found in in the chapter “Tile placement and Planning” . Obviously the same applies to token naming, item naming, etc..
Multiple event*.ini files
When you want to group related events, you can also place them in a separate file. The advantage is that if you have the non alphabetical sorted view, the related events will still be close together in the list:
  

Second advantage is that you can narrow down the search list by selecting the related file in the Source list, making it easier to find your event:
  

To move events to a separate source file all you need to do is click the ‘events.ini’ at the Source:, select {NEW:File} and give it a new filename (or select a file you might have created earlier).

It is a valid question, you could absolutely do it that way and save some time and complexity.

The next question you’ll ask is “Why didn’t we just add these buttons in the event chain above?!”


This is also a valid question, however there is a very subtle reason why it would not work.


The reason we are doing these in two event chains is that “UI Elements” will lay sequentially. If more than one UI element overlaps another, the last one laid will be “on top” therefore if you click, that UI’s action will run. This has it's advantages and disadvantages and is what makes this method complicated. Laying the buttons sequentially above would lay them in this order:


Full screen BG Image
Full Screen Page 1image
Smaller Page 1 Button
Full Screen Page 2 image
Smaller Page 2 Button


If you click the Page 2 button it will trigger it's action, because it's on top and small. If you try to click the Page 1 button, it will do nothing because the full screen image “Full screen Page 2 image” is actually placed on top, despite Page 1 being a small button.


This simple order is what means we have to lay the buttons separately, it's also a nice habit get into, drop all your pretty pictures all perfectly aligned, then slap some haphazardly placed invisible buttons on top.

Alternative Translation Method (Advanced)
Instead of using the editor to translate a scenario, you could do the work all in the Localisation.<language>.txt files. Make use of a source code editor (like Notepad or vscode, freeware). Do not use editors that add hidden formatting attributes (like MSWord).


The high level steps are as follows:
localization.xxx.txt → Translation sheet.
* Copy the Localisation file that is to be translated (this should be the default language) and rename the copied file reflect the translated language 
* Modify the copied file using CTRL + H, click regular expression. Enter ,(.*) into the find field and  \t$1 into the replace field.
* Select all (File Select All) of the text in the newly edited file and copy it to the clipboard
* Create a Spreadsheet (I would recommend a google spreadsheet)
* In the Spreadsheet click in the A1 box and paste the contents of the clipboard.
* Once verified, delete the content from the NotePad file you just copied from (you could just cut the text into the spreadsheet if it's easier)
* Translate the text (optionally use the google translate formula for this, example translate from English to French: =googletranslate(<celreference>;"en";”fr”))
Translation sheet → localization.xxx.txt
* Copy all of the cells in the spreadsheet and paste it back into the empty (copied) localisation file.
* Modify the file using CTRL + H with the regular expression \t and replace all it with the regular expression , .
* Save the file, follow the rest of the process below to add the translation file to the quest.ini and then test it in the editor using your chosen language.

Making your scenario ready for translation
Contributed by antontimmermans


To make future translation of you scenario more easy it will help if you make some texts that you use often (like the text “Continue” on a button) a standard text.Standard text definitions must be placed in  %appdata%\Valkyrie\MoM\Editor\localization.<language>.txt and referenced to in the rest of the file (or valkyrie editor). With this mechanism, a translator only has to translate a word (or sentence) once. 


Note: when you edit these types of files you must use a ‘source code’ editor like for example Notepad++ or atom (both freeware). These editors won’t add any markup code that can mess up your file but do have some spellings checking capabilities.


A standard text definition contains a (unique) reference word and the text it refers to separated by a comma (,). Syntax: <unique reference word>,<display text>


In the standard text examples below, the text in capital letters is the reference word. And the text behind the comma (,) is what will be displayed in the game:
ATTACK,Attack
CANCEL,Cancel
CONTINUE,Continue
EXPLORE,{action} Explore
INSPECT,{action} Inspect
NEVERMIND,"<i>""Nevermind""</i>"
OPEN,{action} Open
PICKUP,{action} Pick-up
SEARCH,{action} Search
To refer to the standard texts you have to use the following syntax {qst:<reference word>}.
Example reference:
EventTESTLightsOn.button1,{qst:CONTINUE}
Important: if you edit this text in a source code editor, do not change anything upto and including the comma (,) or you will lose the reference to the event.
You can also use this reference syntax directly in the valkyrie editor:
  

Note: that when you type the text in the editor it will initially display the {qst:CONTINUE} syntax, but when you leave the event and then go back to it you will see that Valkyrie automatically shows the button text in your chosen language (provided that you put the standard definition text in the localization.<language>.txt file.
Combining multiple standard text to generate a longer description is also possible.
Example:
Default text to be shown when inspecting the item:
ONECLUE,You receive 1 Clue.
CONCLUSIVE,You notice some dried blood on the knife..
The first time you inspect this item you wish to show the text and hand out one clue:
EventQItemConclusiveEvdInspectFrstClueA.text,{qst:CONCLUSIVE} {qst:ONECLUE}
Will show:
You notice some dried blood on the knife. You receive 1 Clue..
The second time you inspect the same item, you only wish to repeat the information but NOT hand out a clue again:
EventQItemConclusiveEvdShowFrstClueA.text,{qst:CONCLUSIVE}
Will show:
You notice some dried blood on the knife..

General Tips
Alternate Endings
Have a think about different ways that the players can complete the game. Do they have to kill a big monster, can they disrupt the ritual before it is summoned, can they burn down the mansion instead? Use your imagination, it will add a lot of flavour to your Scenario.
Late game events
One thing I found when play testing an earlier Scenario, was that late game the board looked very empty. Try adding events that trigger based on the #round number (using the StartRound trigger), this could trigger events that happen in another part of the board that the Investigators may have already investigated. You can use this to remove board tokens, add tokens or spawn monsters. You can also trigger events to remove components like tokens and even tiles.


Story is Key
A general useful tip is not to get precious or hung up about any element of the story. Every element of the story can (and probably will) get changed as long as the core of the story and the horror that arises from it are kept.

For example, let's imagine “The Thing” is your favourite movie and you're all fired up to create an epic Mansions scenario based on the film. Well for a start there are no snowy wastes tiles or ice station rooms or for that matter a 'Thing' monster figure but change the monster to be a Thrall, change the setting to be an abandoned house in say the wilderness and it starts to look more feasible. The key question is what is the essential core of the movie? Well, I think the horror comes not from the scariness of the creature in or of itself but relating to the stress of the characters desperately trying to determine who is infected. Add a mechanism in the app for this and things start to look more interesting - and the randomness has arisen from the core of the story and the horror.

Publishing your Scenario
Before you think about publishing your scenario I will give one bit of advice (outside of tip text no less!).


PLAY TEST!


Play it through, get the board pieces out, set it up and play it over and over. Clear out the spelling mistakes, fix the event sequencing bugs, get it perfect.


Then invite your friends over and invite them to give brutal feedback… Play it, letting them lead so you don’t spoil the Scenario and suck up all of their ideas.


Take the criticism back to your Scenario and add, adjust where you need to to abate their concerns.


I was going to Publish my own Scenario. Play tested with my Wife and that put it right back on the drawing board. You’ll be surprised how linear a Scenario can feel when playing it, compared to writing it.


Only when you and your gaming group are happy, should you proceed to publish! 


Publishing your scenario is the act of uploading it to a persistent (will always be available), publically accessible website. Once it is online, it can be added to the “Download” list on the Valkyrie app.

GitHub
Bruce has suggested using GitHub to publish scenarios. As it's a free and very stable platform (and is what the Valkyrie team uses to develop the application itself!)

To keep this as simple as possible I will use the Windows GitHub Desktop Client. There are 4 simple concepts to understand before using Git(Hub).


Repositories - Is a folders that exist on your computer that you synchronize to a Repository on GitHub.com.
Commit - Is an action where you confirm the changes you have made to files in your local repository (folder on your PC) to be approved to be uploaded to GitHub. I.e you update your Scenario and want to update it on GitHub.com.
Push - Is a command that will mirror your local “commited copies” (see above) to the online GitHub.com repository. Basically “upload the things I have said are OK for upload” (committed).
Pull - This will pull down any changes from GitHub.com to your local PC (imagine you have two PC’s and work on your scenario from different machines, this is a way to keep those two PC’s and GitHub.com in sync).


This is the bare bones that you need to understand to use GitHub, I would encourage you to check out the guide above, if you are curious.

This process explains how to link a Localization.<language>.txt file to your Scenario.


Copy Localization.<language>.txt the Scenario file to your Scenario’s folder.
%appdata%Valkyrie\MoM\Editor\<ScenarioName>


Open the directory and edit the Quest.ini file.


You will notice a section that lists you localization files and the default language:
  

The default language will automatically be set to whichever language your client was set to when you created the scenario. If you wish to change the default language, it can be done here.


Add a new line under the [QuestText] and type the name of the extra Localization.<language>.txt


Save and Exit the file.


Open Valkyrie > Scenario Editor > Your Scenario
Click Tools and Create Package


The new package will now contain the additional language.
Copy these files to your online repository (copy to local repository and commit changes if you are using GitHub).

Appendix; Advanced tips and tricks, Code Snippets, and Templates
Contributed by antontimmermans


Advanced scenario programmers may choose to edit the source code files directly to save time. Files like %appdata%Valkyrie\MoM\Editor\<ScenarioName>\event.ini and %appdata%Valkyrie\MoM\Editor\<ScenarioName>\localization.<language>.txt.


If you plan to edit those files make sure that you do not use an editor that adds additional markup which could mess up your files. You should use a source code editor like for example Notepad++ or atom which are both free to use. After editing the files you can reload the scenario in valkyrie and see the result.


IMPORTANT: Any typo in the syntax may result in loss of (part off) your work or unexpected application behavior. Make sure to make regular back-ups. If you are uncertain how this works, you should continue using the valkyrie editor only.

Introduction UI - the prologue
(contributed by Anton Timmermans with thanks to EwinDC for his example and explanation)
This chapter will give you the images, positions and sizes of the UI elements to mimic the opening screens of the FFC application. Obviously, it is not mandatory to use these settings and images, you can use your own imagination to make whatever you want. However, you must take into account that the game will be played on big AND small screens, and with aspect ratios of 16*9 AND 16*10.
This layout does not add the frame around the picture like in the FFC app. This is to allow for more variety in sizes of images and not to be limited to the rectangular shape. And I found it near impossible to get the frame around my chosen image without making my own frame.
Prologue Layout
These two images show the result of the chosen settings in a 16*10 ratio (left image with yellow numbers) and a 16*9 ratio.
  
  

Let’s start with identifying the elements that make up the prologue screen. The numbered elements in the layout correspond with the order and numbered items in the picture and list below. The order of placement is important as UI elements are placed on top of eachother.
  

1. UIntroductionBackground
2. UIIntroductionTextTop
3. UIIntroducitonContinueBackground
4. UIIntroductionContinueText
5. UIIntroductionImage
6. UIIntroductionText


Note: in the following chapters the placement of the elements is always done from the center position and Units set to vertical. This ensures that the scaling and positioning of the UI elements works with any aspect ratio. 
UIIntroducitonBackground  
First, I start with placing the green background. I choose the ImageGreenBG from the built-in images because it completely fills the screen and allows for any shape and format introduction image. 


Note: chapter UIIntroductionImage contains an alternative for the background. 










UIIntroductionTextTop  
The second element I place, is the curly bar that decorates the top of the text. I choose the ImageCutsceneTextTopper image from the built-in images, which is the same as used in the standard FFC app. The chosen size and position will align it with the textbox that will be placed later.






  

UIIntroductionContinueBackground  
Third placement is the frame that will outline the ‘Continue’ button. The image that is from the build-in images: ImageInvestigatorSelectTile. It’s location and size are important because they have to align perfectly with the text ‘Continue’ that will be placed on top of it later. The FFC app uses a different image, but I haven’t discovered that one yet in Valkyrie.
  

UIIntroductionContinueText  
The fourth element to place is the ‘Continue’ button.
This will be the active button that will be clicked to continue the scenario. The placement, size and aspect aligns this button with the white area of the  UIIntroductionContinueBackground image that was placed earlier. The text size should be 1 and the colour Black to make it nicely readable with the light background.


Note: It is also the active element on the Prologue screen which should clean up the UI elements (as shown in the images) and place the initial start tile to get the scenario started.
  
  

UIIntroductionImage  
Fifth element to place, is the picture to illustrate the story. The position makes it fit nicely next to the text on the page. You can choose your own image or a built-in image. The location is strongly advised, but the size depends on your chosen image. I found it easiest to first remove the ‘-’ on the x position, size the image and then put the ‘-’ back.
  



Note that if you want to mimic the FFC app more, then you should place this image BEFORE UIIntroducitonBackground and choose image ImageCutsceneBG from the built-in images as background. The image that you choose should than be rectangular in shape or placed in such a way that the ‘window’ in this background image shows the correct part of your image.


UIIntroductionText  
Last but not least I add the prologue text. The displayed position, size and aspect will create a text box that aligns between the UIIntroductionContinueBackground and UIIntroductionTextTop. You can play a little with the Text Size depending on how much text you have. Just make sure it fits in the box.

User Created Triggers
Contributed by Nicola Zee after some encouragement.
Valkyrie is event driven.  The first event is triggered by the EventStart trigger and the next event follows on from the first event (either automatically or when the specified button is clicked).  The next event follows on from the second event and so on and so on until the scenario ends.  As the saying goes, “it’s just one damn thing after another”.   This is the heart of how Valkyrie works and in nearly all cases it works great.
Doing more than one thing at the same time.
Very occasionally, having more than one event trigger at the same time is useful.  This can be done using triggers created by the user.  How to create such triggers is covered earlier in the manual in the section on Variable Types and @Variables.  Instead I will provide some examples of advanced usage of user created triggers.
Example 1: Assigning Roles to Allies
Imagine two Allies (A and B).   One Ally is set to Role 1 and the other Ally is set to Role 2.
This can be done by using 2 events (called randomly by another event).  The first event sets Ally A to Role 1 and Ally B to 2 and the second sets Ally A to 2 and Ally B to 1....
Event_AllyAsetRole1_AllyBsetRole2
Event_AllyAsetRole2_AllyBsetRole1


An alternative way of doing this is to use two triggers.  Both triggers fire off at the same time.  In the following code, the two triggers are @SetRole1 and @SetRole2.   Setting @SetRole1 and @SetRole2 causes both events to happen at about the same time.  When one of the allies is set to a role, the ally’s role will not be set again because a variable prevents the event from being called again.  The variable tempRole is set to a number 1 for setting a random Ally to Role 1.
 
[EventSetRoles]
display=false
buttons=1
event1=
trigger=EventStart
operations=@SetRole1,=,1 @SetRole2,=,1
 
[EventSetRole1]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB
trigger=VarSetRole1                               <-- Triggered by setting @SetRole1 to 1
operations=tempRole,=,1
randomevents=true
 
[EventSetRole2]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB
trigger=VarSetRole2                       <-Triggered by setting @SetRole2 to 1
operations=tempRole,=,2
randomevents=true
 
[EventSetRoleAllyA]
display=false
buttons=0
operations=AllyASet,=,1 AllyARole,=,tempRole
conditions=AllyASet,==,0
 
[EventSetRoleAllyB]
display=false
buttons=0
operations=AllyBSet,=,1 AllyBRole,=,tempRole
conditions=AllyBSet,==,0


The Event Combination Explosion Problem
The solution using triggers is clearly worse than the first when there are only two combinations.  It is more code, more complicated and may be subject to strange and hard to track down bugs.  But what about if the number of Allies increases to 5?  Well, the number of combinations increases by a lot more than 5 and the script becomes confusing.
         Event_AllyAsetRole1_AllyBsetRole2_AllyCsetRole3_AllyDsetRole4_AllyEsetRole5
          Event_AllyAsetRole1_AllyBsetRole2_AllyCsetRole3_AllyDsetRole5_AllyEsetRole4
         Event_AllyAsetRole1_AllyBsetRole2_AllyCsetRole4_AllyDsetRole3_AllyEsetRole5
And so on for several more lines!  The problem occurs because every combination must be scripted as a separate event.


 
The trigger solution needs just 10 events because each event is fired off at the same time.
 
[EventSetRoles]
display=false
buttons=1
event1=
trigger=EventStart
operations=@SetRole1,=,1 @SetRole2,=,1 @SetRole3,=,1 @SetRole4,=,1 @SetRole5,=,1
 


[EventSetRole1]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB EventSetRoleAllyC EventSetRoleAllyD EventSetRoleAllyE
trigger=VarSetRole1                               <-- Triggered by setting @SetRole1 to 1
operations=tempRole,=,1
randomevents=true


[EventSetRole2]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB EventSetRoleAllyC EventSetRoleAllyD EventSetRoleAllyE
trigger=VarSetRole2                              <-- Triggered by setting @SetRole2 to 1
operations=tempRole,=,2
randomevents=true


[EventSetRole3]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB EventSetRoleAllyC EventSetRoleAllyD EventSetRoleAllyE
trigger=VarSetRole3                               <-- Triggered by setting @SetRole3 to 1
operations=tempRole,=,3
randomevents=true


[EventSetRole4]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB EventSetRoleAllyC EventSetRoleAllyD EventSetRoleAllyE
trigger=VarSetRole4                               <-- Triggered by setting @SetRole4 to 1
operations=tempRole,=,4
randomevents=true


[EventSetRole5]
display=false
buttons=1
event1=EventSetRoleAllyA EventSetRoleAllyB EventSetRoleAllyC EventSetRoleAllyD EventSetRoleAllyE
trigger=VarSetRole5                               <-- Triggered by setting @SetRole5 to 1
operations=tempRole,=,5
randomevents=true

Example 2: Multiple Door\Sight Tokens
The second example involves checking if a door\sight token needs to be placed depending upon whether the tile being placed is visible.  Imagine there is a bedroom tile, a hall tile and a door between the two.  Doors from the foyer lead into the hall and the bedroom.  There are four pathways.
1.      Enter the hall from the foyer and, then, the bedroom from the foyer.
2.      Enter the bedroom from the foyer and, then, the hall from the foyer.
3.      Enter the hall from the foyer and, then, the bedroom from the hall.
4.      Enter the bedroom from the foyer and, then, the hall from the bedroom.
This problem can be solved by using standard events using an event per pathway.   This is described in the section Multiple entry possibilities to a tile.   An important part of the solution is that multiple combinations can occur and must be scripted for.  An alternative solution to the problem is provided by using user-created triggers.  On placing a tile, the doors going into the room are removed.  The doors going out are placed only if the tile is visible.
 
[EventPlaceBedroom]
buttons=1
event1=
add=TileBedroom
remove=TokenFoyerToBedroom TokenHallToBedroom
operations=BedroomVisible,=,1 @PlaceBedroomToHall,=,1
 
[EventPlaceHall]
buttons=1
event1=
add=TileHall
remove=TokenFoyerToHall TokenBedroomToHall
operations=HallVisible,=,1 @PlaceHallToBedroom,=,1
 
[EventPlaceBedroomToHall]
display=false
buttons=0
add=TokenBedroomToHall
trigger=VarPlaceBedroomToHall             <-- Called by setting @PlaceBedroomToHall to 1
conditions=HallVisible,==,0
 
[EventPlaceHallToBedroom]
display=false
buttons=0
add=TokenHallToBedroom                    
trigger=VarPlaceHallToBedroom        <-- Called by setting @PlaceHallToBedroom to 1
conditions=BedroomVisible,==,0
 
If an investigator enters the Hall, the event EventPlaceHall runs.  The event removes all tokens for ways into the Hall and the event @PlaceHallToBedroom is triggered.  The triggered event checks if the door from the Hall to the Bedroom needs to be placed.   The critical part of the logic is that (if the Bedroom is already visible) the door from the Hall into the Bedroom is not placed.
 
The Event Combination Explosion Problem Again
 
The use of triggers in the second example is elegant but it is not essential.  It really starts to pay off when there are multiple pathways.   Once again imagine a door between the hall and the bedroom and doors from the foyer leading into these two rooms.   Now imagine that the hall and the bedroom can be accessed from a room which is not the foyer and the foyer can be accessed from another pathway.  With triggers, adding the extra doors is trivial because all that is needed is to add a trigger for each door.  For example, all that is needed for the door from the Bedroom to the Foyer is another trigger.
 
[EventPlaceBedroom]
buttons=1
event1=
add=TileBedroom
remove=TokenHallToBedroom TokenFoyerToBedroom
operations=BedroomVisible,=,1 @PlaceBedroomToHall1,=,1 @PlaceBedroomToFoyer,=,1


Then all that is needed is that the triggered event checks if the tile is visible.  In effect, we have created a way to only place a door if the tile the door leads into is visible.


[EventPlaceBedroomToFoyer]]
display=false
buttons=0
add=TokenBedroomToFoyer
trigger=VarPlaceBedroomToFoyer             <-- Called by setting @PlaceBedroomToFoyer to 1
conditions=FoyerVisible,==,0
 
Example 3: Placement of Multiple Optional Tokens
Imagine there are 6 Allies that move around the rooms of a map.  Once again we can try to script using standard events the various possible combinations of placements.  But, by using triggers we can make an elegant solution.  The solution is similar to checking for the placement of door tokens but, instead of checking if a tile is already visible, we need to check if the ally will be visible in the room to be placed.




User Defined Triggers Conclusion  
User defined triggers should be used rarely.  Most problems do not need them and they can lead to strange and hard to track down bugs.   But if you find your solution involves scripting a large number of very similar events for a large number of combinations, consider if you can avoid the combination explosion by creating your own triggers.
